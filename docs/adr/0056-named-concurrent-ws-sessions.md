# ADR-0056: Named and concurrent `sc ws` sessions (P20, #215)

- **Status:** Accepted (built, including workspace refresh)
- **Date:** 2026-10-20
- **Phase:** 20 (follow-on)
- **Builds on:** ADR-0030 (agent sessions), ADR-0050 (sessions on partial clones), ADR-0023 (agent workspaces), ADR-0043 (per-checkout protected cache)

## Context

ADR-0030 allows one unnamed session per repo: `sc ws fork` writes `.sc/ws/session.toml` and `.sc/ws/<i>/`, and refuses while a manifest exists. Two agent teams working on the same repo cannot each hold a session, and issue #215 asks for named, concurrently open sessions and a way to move a workspace onto a newer tip.

Reading the code turned up one fact that shapes the design. `Repo::open` takes the single-writer lock (`.sc/lock`) for the life of the process, and `sc ws run` spawned the agent command while its `Repo` was still open. While an agent ran in one workspace, every other `sc` command on the repo (`list`, `harvest`, `abandon`, another `run`) failed with `Locked`. Two sessions could exist on disk but not be used at the same time.

## Decisions

1. **Named sessions are additive.** `sc ws fork --name <n>` opens a session called `<n>`. Omitting `--name` addresses the unnamed session exactly as before. A name takes the branch-name grammar (`validate_branch_name`): it becomes a directory under `.sc/` and the prefix of the session's fallback branches. A name that is already open is refused with the existing "already open" message plus the name and the `abandon --session` command to run. Forking the unnamed session while only named ones are open is allowed, and the reverse too.

2. **Addressing.** A session is picked with `--session <n>` on `list`, `run`, `harvest` and `abandon`; a workspace inside it stays addressed by its index (`run <i>`, `abandon [<i>]`). With no `--session` the command means the unnamed session. It never guesses a named one: if only named sessions are open, the error lists them and says to pass `--session`. `sc ws list` with no flag prints every open session (the unnamed one first, then named ones sorted by name); the unnamed session's header line is unchanged.

3. **On-disk layout: no migration.** The unnamed session keeps `.sc/ws/session.toml`, `.sc/ws/<i>/` and `.sc/ws/cache-<i>`, byte for byte. A named session lives in a sibling root, `.sc/ws-<name>/`, with the same inner shape. A sibling and not a child, so every teardown (`remove_dir_all` of a session root on abandon, harvest end and fork-residue cleanup) touches only its own session, and no reserved names are needed inside a root. The manifest format is unchanged; the session name is derived from the directory and never stored. A `.sc/ws-*` entry that is not a directory, whose name is not a valid session name, or that has no manifest is ignored (crash residue or a stray file), so it cannot break `list` or gc. A name given with `--session` is validated before any path is built, so `..` cannot leave `.sc/`. On a case-insensitive filesystem `A` and `a` are the same directory: forking `A` while `a` is open is refused, but `--session A` addresses `a` and names its fallback branches `A-<i>`.
   - Downgrade hazard: a binary from before this change does not look at `.sc/ws-*`, so its `sc gc` would not root a named session's base snapshot. Do not run an old `sc` against a repo with named sessions open.

4. **Fallback branches and labels follow the name.** The unnamed session still falls back to `work-<i>`. A named session falls back to `<name>-<i>`, and `SC_WORKSPACE` is the same string, matching `sc work --name` and the ADR-0030 rule that the label equals the branch name. The existing collision suffix (`-2`, `-3`) still applies, so a clash across sessions (for example a session named `work`) cannot overwrite a branch. The candidate commit message is `ws-<i> harvest` (unnamed) or `ws <name>-<i> harvest`.

5. **Concurrency: serialized by the repo lock, with the lock released while an agent runs.**
   - Fork, harvest and abandon run under the repo lock for the whole command. Two harvests therefore never overlap; the second `sc` process gets `Locked` and nothing has changed. Each harvest builds its candidate from its own session's fork-time base and probes it against the landing tip as it is then, so the existing logic already covers "the branch moved on since fork". No new merge code.
   - **Outcome rule.** Within a session, workspaces land in ascending index order (ADR-0030). Across sessions, the order is the order the harvests are invoked: the first lands, a later one merges cleanly over it or, when its change conflicts, falls back to its own `<name>-<i>` branch and leaves the landing branch untouched. Disjoint edits land to the same tree in either order; overlapping edits go to whoever harvests first. There is no implicit ordering and no `harvest --all`; a script that wants a fixed order calls `harvest --session` in that order.
   - Each session has its own manifest, so no manifest is shared between sessions. Abandoning or harvesting one session never writes another's files.
   - **`sc ws run` no longer holds the lock while the command runs.** `Repo::ws_run_plan` resolves the live workspace, its label and (with `--with-secrets`) the decrypted environment under the lock; the CLI drops the repo and then spawns the command (`WsRunPlan::run`). Other sessions can be listed, harvested or abandoned meanwhile. `Repo::ws_run` stays as the two steps together for library callers.
   - **A live command marks its workspace busy.** Because the lock is no longer held, harvest and abandon could now run against a workspace an agent is still writing. `ws_run_plan` therefore creates `<session root>/running-<i>` exclusively (beside the checkout like the cache), holding the owning `sc` pid; once the command is spawned the marker also records the child's pid, so an orphaned command keeps the workspace busy after `sc` is killed. `WsRunPlan` removes the marker when the command ends or the plan is dropped. Harvest and abandon of that session refuse before reading or removing anything while any recorded pid is alive or the marker is unreadable; a marker whose pids are all provably dead is cleared (the `RepoLock` probe; on non-unix it stays, and the error names the file). A second `ws run` in the same workspace is refused. Other workspaces and sessions are unaffected. The marker covers `sc ws run` only: an agent started by hand in the checkout directory, as ADR-0030 always allowed, is not tracked.
  - **A command in a workspace can reach the host repo.** A workspace lives under the host's `.sc/`, so `sc` run from inside it finds the host repo (`Layout::discover` walks up). With the lock released, such a command can now succeed (before, it failed with `Locked`), and `sc commit` or `sc switch` there acts on the host working tree and branches. A hand-started agent already had this. The tool does not guard against it; it is not an isolation boundary (compare ADR-0050).

6. **Protected caches.** `Layout::ws_cache_path(session, i)` is `<session root>/cache-<i>`, beside the checkout like before, so each session's stat caches live and die with that session. Nothing else about ADR-0043 changes: the cache is never committed or transferred, and a lost cache costs a re-seal, not correctness.

7. **Sparse view and partial clones.** Each session records the host's sparse spec in its own manifest at fork, and harvest diffs and commits against that recorded view (ADR-0030's fork-time rule, per session). ADR-0050 holds per session: fork fills the view or refuses with the gap error before anything is written, a harvest grafts out-of-view subtrees from its base, and landing uses the ADR-0049 merge. Two sessions forked under different host views each keep their own.

8. **gc.** Every open session's base snapshot is a gc root (`list_sessions`), not only the unnamed one.

9. **`sc work` is unchanged.** It uses temporary directories and never touches `.sc/ws*`.

## Workspace refresh (built)

`sc ws refresh [--session <n>] [--onto <branch>] [--identity <key>]` moves a live session onto a newer tip and keeps what the agents did. The first draft of this section (candidate commit, replay with the ADR-0049 engine, refuse on any conflict) held up; building it settled the two open points and added the rules below.

1. **No new merge entry point was needed.** `replay_commit` (the cherry-pick engine) already merges a snapshot onto a tree without touching the host's working tree or a ref, and on a partial clone it goes through `tree_merge_filled`. A workspace has no commits of its own, so its state is its checkout: refresh commits each checkout to a throwaway candidate with harvest's pipeline (`workspace_candidate`, harvest's body minus the branch write: scanner gate, protected re-encryption, the workspace cache), whose parent is the session's base. The candidate is replayed onto the new tip, which is base to tip on the host's side and base to checkout on the workspace's. The secret registry is not merged: a checkout cannot change it, so the candidate carries the base's.

2. **Uncommitted edits are part of the replay, and stay edits.** Refresh creates no commit and no ref. After it the workspace holds the merged tree, its recorded base is the new tip, and `sc ws list` shows `changed` for exactly what the agent added on top of that tip. A later harvest builds its candidate on the new tip and lands as a fast-forward of it (or a merge, if the branch moved again). An unchanged workspace is simply laid out at the new tip.

3. **Session-wide, not per workspace.** The manifest has one `base_snapshot` for the session. Refreshing a single workspace would need a per-entry base (a schema change touching `ws_changed_for`, harvest and gc roots), which this does not do. `sc ws refresh` therefore takes every live workspace of the session (`--session` picks the session). A per-index form is deferred.

4. **The target is the checked-out branch's tip, or `--onto <branch>`.** Refresh reads the tip from the store and does not touch the host's working tree, so it needs neither a clean tree nor the branch checked out. The session's `base_branch` (harvest's default landing branch) becomes the target branch. It refuses when the target is a private branch (the checked-out one by default, or the `--onto` one; an explicit public target works with a private HEAD) and during a stopped merge/pick/rebase (as harvest does). With the session already at the target, it does nothing.

5. **Everything that can refuse is decided before the first write.** A workspace running a command (the `running-<i>` marker, `ensure_idle`) aborts at once, as do a view gap (the view is filled first on a lazy clone, else the gap error of ADR-0050) and any non-policy error. The rest is collected across all workspaces and reported together, with workspace and paths: a candidate rejected by the scanner; any conflict, in or out of the view; a protected path that needs an identity to merge (`ProtectedMergeNeedsIdentity`, `NotAuthorized`) or a file/directory collision; a protected path the new tip changed that the supplied identity cannot decrypt while the workspace holds a plaintext copy (`--identity` hint; a path the workspace never had, because it was forked without a key, is skipped and reported); a result whose `.scignore` differs from the checkout's and stops hiding a file the old rules hid (so the candidate never saw it: the next harvest would commit it, whatever it holds; the refusal names the paths, and is skipped when the rule file is unchanged); a file the workspace added that the result's own `.scignore` would hide (a harvest reads the workspace under the ignore rules on disk and exempts only what its base tracks, so once the base is the tip the file would stay on disk and never land; the refusal names the paths); a user's file or directory where the new tip adds one (`refuse_untracked_overwrite`'s rule, extended to ignored files: an ignored file with the target's exact bytes still refuses, and so does an empty directory that no removal emptied); a path whose plaintext the workspace holds (a regular file is on disk) that the new tip lists with the same ciphertext but without the protection flag, or without a covering rule in the replay result's protection or in the tip's own (the session is based on the tip, and the result merges both sides' rules, so it can still hold one the tip dropped: a downgrade a harvest would publish; a protected path with no file on disk, from a workspace forked without a key, is not refused; checked before an unchanged entry is skipped, so a rule dropped from the tip's policy with the entry untouched refuses too; the opposite, a rule added for a path the tree still lists as a plain file, is not a refusal: nothing is written, and any later commit seals the file under the new rule, ADR-0025); and a file that must be replaced no longer holding what the candidate read. A scanner hit refuses the refresh, as the earlier draft proposed; the agent fixes the file and retries.

6. **Re-materialize in place, only where the tracked content differs, using the ADR-0034 refinement 8 rule, checked twice.** The planner compares the candidate's tree with the replayed tree under the session's recorded view (both walks bounded by it, so an out-of-view subtree a partial clone never fetched is not read; `materialize`'s own old-root walk is unbounded on a workspace layout, which is why it is not used). Only a path whose blob or mode differs is touched; an untouched file keeps its inode and mtime, and untracked or ignored files are never looked at. The plan records, for every path it will touch, what the candidate read there, and the same check runs again immediately before each removal or write, because the plan is made well before the write (replay, a lazy fill and the other workspaces' plans sit in between) and nothing stops an editor or an agent working in the directory: a plain file must still have exactly the candidate's bytes; a randomized protected file must still match the workspace cache's keyed tag for the candidate's blob (the proof commit uses); a convergent one must still re-encrypt to the candidate's blob; a tracked plain file that has since disappeared counts as changed. A parent directory swapped for a symlink since the plan also stops it. On a mismatch the refresh stops with the file untouched. The check and the write are not atomic: an edit in the instant between them can still be overwritten, which no scheme without a lock on the file can close. Each write is atomic (temp file, rename), so an interrupted refresh never leaves a half-written file. A protected file written is recorded in the workspace's `cache-<i>` as fork does, and the caches are saved after the manifest. A removal that empties a directory removes the directory (`remove_dir`, so only directories the removals emptied).

7. **Crash behaviour.** Write order: a `pending_refresh` marker in the manifest (durable, before the first file), every checkout, then the manifest with the new base and no marker. The marker records the target tip and its branch and, per workspace, two snapshots: the candidate (the checkout as the refresh read it, parent the old base) and the result (the candidate replayed onto the target; a snapshot so its wrap lists come with it). All of them are gc roots. If the first file operation is refused, the marker is cleared again (or, on a retry, left as it was). In-place re-materialization is not atomic across files, and no in-place scheme can be. A crash leaves the old base, the marker, and each checkout a mix of files at their pre-refresh state and at their result state.

   A mix cannot be re-read as a fresh checkout. A merged file (the agent's line 4 and the host's line 5, say) diffed against the old base fuses the two edits into one hunk that overlaps the tip's, and conflicts with the very tip it was merged with; and a harvest would read the refreshed files as the agent's own work, re-applying a part of the tip the host has since reverted, or diverging on a refreshed protected file that has no cache proof against the old base. So while the marker is set, `sc ws run` and `sc ws harvest` refuse ("run `sc ws refresh` to finish it"), `sc ws list` says so, and abandon still works. `sc ws refresh` run again does not recompute anything from the checkouts: it re-plans from the recorded pairs, over the same candidate and result, and accepts at each path either the bytes the candidate read or the bytes the result holds (a plain file by bytes; a protected file by decrypting the result's blob and comparing plaintext when a key is given, which needs no record, else a randomized one by the workspace cache and a convergent one by re-encrypting; the same holds for what the candidate read, opened with the wrap lists of the candidate snapshot, so the agent's re-sealed edit of a protected file is recognised even when the cache on disk predates the refresh; the caches are also saved before the marker is written and right after each protected write, because a kill never reaches a later save). Without a key a retry that finds a protected file it cannot verify refuses with "pass --identity (an unfinished refresh needs the key to be resumed)". A path already holding the result is left alone, including a file the first attempt added, so an interruption is resumed to the same end state (a directory the first attempt emptied, because the result replaces `dir/file` with a file `dir` and the crash came between the removals and the write, is replaced on the retry: on a retry an empty directory counts as the refresh's own when the candidate tracked files under it that the result drops; a directory with anything of the user's in it still refuses, and a protected file the candidate tracked does not count, since it may never have been laid out, #275); an edit made to a file the first attempt wrote or was about to write is neither of the two and still refuses. Only then does it move on to the requested tip, as a fresh refresh from the finished state, so a host revert in between is honoured. A protected path the first attempt had not yet reached still needs `--identity`. The target branch is part of the marker, so the unfinished step is labelled as the branch it was moving to.

   `atomic_write_durable` stages each write in `<stem>.<pid>.<n>.tmp` beside the file; a writer killed mid-write leaves one, possibly holding protected plaintext, where a harvest would take it for the agent's file. The marker records the pid of every process that wrote for the refresh (the first attempt and each retry); the retry removes files of exactly that name, for every path the result changes (skipped ones included), under one of those pids once it is provably dead, and nothing else, and does so before the `.scignore` comparison, so a refresh that turned `*.tmp` from hidden to visible does not count its own staging file as a file the agent added (#275). The sweep runs while the retry is planned, so a retry that then refuses may already have removed those dead writers' files; nothing else is touched. The alternative that leaves the old checkout whole (build the new one in a sibling directory and swap) was rejected: it drops untracked and ignored files, breaks any open handle or working directory, and is no more atomic in the face of a crash during the swap. While the marker is set the manifest's `base_snapshot` holds the text `refresh-unfinished` (the real base is in the marker), so a binary from before this change fails to parse the manifest instead of harvesting a half-refreshed checkout as clean, and so does its gc.

Known limits: `sc ws run --with-secrets` resolves the secret environment from the host's checked-out branch, as it did before refresh existed, not from the session's base; on a case-insensitive filesystem a target that renames a tracked path only by case is refused (the old spelling is found on disk but not tracked under the new one; fail closed, as the other untracked-file guards are); the marker records no per-file progress, so a file the interrupted refresh added and the agent then deleted before the retry comes back (the retry cannot tell its own earlier write from a file the result still owes); for the same reason, if a crash came before the removals, a user who then deletes the tracked files under `dir` and puts an empty directory of their own at `dir` loses that empty directory to the retry, which takes it for the husk of its own removals (no content is ever lost); deletions and the pruning of emptied directories are not fsynced before the manifest is written, and a file's mode is applied just after its rename, so a power loss (not a process crash) can leave a refreshed file briefly without its mode or a deleted file back, both of which the retry redoes from its record. When a retry finishes an older target first and the requested one is then refused, the older target's progress is kept but not reported. A mode-only edit in a workspace is not seen as a change (harvest's diff compares content only, `diff_worktree`), so where the new tip also changes that file's content the tip's mode wins, as a harvest would drop the mode edit. Not built: refreshing one workspace by index.

Tests: `ws_refresh.rs` (no edits; already at the tip; uncommitted edits and a same-file merge, then a harvest that lands as a fast-forward of the new tip; host and workspace deletions; a conflict refuses everything and harvest is unchanged; a running command; two named sessions refresh independently; `--onto`; an ignored file survives and a user file in the way refuses; the scanner; protected paths need `--identity`, the cache keeps an untouched workspace unchanged and an edited protected file changed; a narrow recorded view; a file edited after the plan (plain and protected) is not overwritten and leaves nothing pending; an injected mid-apply failure blocks harvest, can be abandoned, can be run again, and finishes onto the old target after the host reverted part of it; the same with a protected file that needs the key; emptied directories go), `partial_sessions.rs` (a partial clone: the view is refreshed and `docs/` is carried and never fetched; a gap refuses before any write), `crates/cli/tests/ws_sessions.rs` and `demo/run_ws_demo.sh` section 10.

## Consequences

- Several named sessions can be open at once and used in parallel, including while an agent command runs, with deterministic first-harvest-wins outcomes.
- Existing repos and scripts keep working untouched: the unnamed layout, command lines, output, `work-<i>` names and manifests are the same.
- A harvest that finds the landing branch moved by another session's landing takes the ordinary merge path; conflicts end up as `<name>-<i>` branches for manual `sc merge`.
- Not built: `harvest --all`, per-index refresh, and a per-entry record of the branch a workspace landed on (the existing `sc ws list` caveat about `--into` stands).

## Alternatives considered

- **Nest named sessions under `.sc/ws/<name>/`:** every `remove_dir_all(.sc/ws)` would take other sessions with it, and names would need reserving against `session.toml`, `cache-*` and digits. Rejected for the sibling root.
- **One manifest holding several sessions, base per workspace:** a schema change that needs a migration path and makes every manifest write a shared read-modify-write. Rejected.
- **Pick the only named session when no `--session` is given:** convenient, but a script's meaning would change when a second session is opened. Rejected for an explicit error.
- **A second lock for harvest instead of the repo lock:** the repo lock already serializes every writer and is held across the whole harvest. Rejected as redundant.
- **Make the lock re-entrant or per-session:** a much larger change to a core invariant. Releasing it around the child process is enough.

## Tests

`ws.rs`: named and unnamed sessions coexist in separate roots with their own cache paths; collisions and invalid names are refused; addressing a missing session lists what is open and never guesses; the first of two conflicting harvests wins and the second falls back to `<name>-1`, in both orders; disjoint sessions land to the same tree in either order; abandoning one session leaves another's checkout, edit and manifest intact and still runnable and harvestable; `SC_WORKSPACE` and fallback branches carry the name and are suffixed on a clash; gc roots every open base; a live `ws run` blocks harvest and abandon of its own session only, a dropped plan or a dead holder releases it; a `--session` with path components is refused, and a stray `.sc/ws-*` file does not break listing or gc. `partial_sessions.rs`: two named sessions on a partial clone see only the view, land one after the other, and carry `docs/` unread. `crates/cli/tests/ws_sessions.rs`: the same through the binary, plus listing and harvesting another session from inside a running `sc ws run`. `demo/run_ws_demo.sh` gains a named-sessions section.
